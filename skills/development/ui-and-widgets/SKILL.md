# Interfaces et widgets

Lire les [règles communes et la phase autorisée](../../README.md), le [standard de module](../../../docs/STANDARD-MODULE.md), les [parcours](../../../docs/USER-STORIES.md) et le [contrat conversationnel](../../../docs/COMPATIBILITE-CHATGPT.md). Avant le GO, préparer contributions, états et recettes, sans annoncer une interface fonctionnelle.

1. Réutiliser les composants et mécanismes déjà qualifiés. Les vues workspace utilisent le SDK de panneaux : identité, URL locale, historique, activité et invalidation. Aucun contexte privé Next/Vinext dans un module, aucune réécriture du chat standard pour un métier. Les raccordements à l'hôte restent dans son adaptateur.

   Pour l'administration et les modules natifs, utiliser comme référence les composants et comportements du Creezio original. Conserver leur rendu en adaptant les dépendances techniques ; ne pas substituer une nouvelle interface minimale ni prendre Lite comme base produit. La recette compare les interactions et la présentation effectivement reprises, pas seulement le fonctionnement d'une fixture.
2. Déclarer routes, navigation, droits, exports et emplacements dans le registre UI. Les thèmes compatibles composent les vues permises automatiquement ; un front headless libre ne reçoit pas de modification implicite. Le workspace peut servir un opérateur métier sans lui donner les pouvoirs administratifs.

   Pour le front thémé, déclarer `ui.themes` et ses emplacements supportés ; le codeRef reste relatif au module. Utiliser `sdk/front` et la projection native app, sans importer l'admin dans le thème. Les slots ne possèdent pas d'entrée implicite : leur vue accepte une entrée vide et une identité sans paramètres. Les props publiques sont de présentation seulement ; ne pas construire de session ni de client privilégié pour une vue anonyme. Préserver `application/config` et `application/frontend` lors des mises à jour de thème.
3. Déclarer plusieurs types/instances de widgets et le mode de chaque action selon [le contrat des interactions](../../../docs/INTERACTIONS-WIDGETS.md) : message proposé/envoyé volontairement, contexte du prochain tour sans tour LLM ni mutation, ou traitement direct. Combiner les modes si utile, sans repli silencieux changeant l'effet. Les opérations métier effectives utilisent les mêmes services depuis écran, front et widget. Vérifier les droits côté serveur à chaque opération métier ; le rendu ou le masquage d'un bouton n'est pas une autorisation. Le widget affiche des données validées, jamais du code produit par le modèle.
4. Distinguer schéma du widget, révision interactive, snapshot d'un message et version actuelle de l'objet. Prévoir états chargement/vide/erreur, action répétée, objet modifié ou supprimé, module désactivé et reprise de conversation. Les anciens messages ne sont pas réécrits à chaque mutation.
5. Conserver brouillons, filtres, scroll et historique pendant les bascules de panneaux ; neutraliser les portails inactifs. Purger les caches devenus interdits lors d'une révocation ou d'un changement d'identité. Une mutation externe ne doit pas écraser silencieusement une saisie.

   Pour les vues ciblant SDK 1.2, utiliser le journal public `@creezio/sdk/operations/command-journal` : déclarer `pending` dans le schéma du panneau, persister avant émission et préserver ce champ dans chaque sauvegarde de navigation. Lier restauration et rendu à la session vérifiée, à l'audience et au contexte ; attendre l'hydratation sans consommer l'état sauvegardé sous un scope anonyme. Une issue inconnue bloque une nouvelle mutation et se relit avec `status`, sans replay ; un refus de statut ne libère pas le verrou. Les tests doivent couvrir persistance refusée, hydratation différée, changement réel de scope et inspection. Vérifier l'export de l'archive effectivement installée ; une version candidate source n'actualise pas un SDK déjà publié.
6. Préparer la ressource MCP Apps et ses audiences depuis le contrat du module. Les skills conversationnels guident les utilisateurs ; ils ne remplacent pas ces guides de développement. Distinguer rendu dans Creezio, test du pont et recette réelle dans ChatGPT.

   Le compilateur `scripts/widgets/compile.mjs` dérive les outils, le type de chaque opération et son champ d'idempotence ; ne pas dupliquer ces valeurs dans le widget. Utiliser le pont et le provider `sdk/widgets` : aucun HTML privé dans le bundle public, aucune clé fournisseur ou session dans l'iframe. Une commande est journalisée avant envoi avec la clé hôte dans le champ canonique ; une query ne reçoit pas une clé ajoutée à son entrée. Le cœur crée le pointeur `renderExecution` après succès connu ; restaurer son résultat par une lecture autorisée, sans réexécuter l'opération ni remplacer silencieusement une ressource historique. Voir [la réalisation T16](../../../docs/IMPLEMENTATION-T16.md) pour les limites de qualification.

   Avec le contrat SDK 1.5, un outil appelé directement par plusieurs widgets déclare `widgetCalls` ; réserver `widget` au rendu initial. Pour afficher une image privée liée, employer l'opt-in de catégorie `linkedRead.mcpImage`, pas une route métier ni une URL publique créée pour le chat. Seul `_meta` réserve les octets au composant ; `content` reste visible du modèle même pour un outil app-only. Vérifier MIME et taille, réponses périmées, révocation des URL Blob et absence d'octets dans le contexte ou la persistance. La recette ChatGPT reste distincte de celle du pont local.

   Tester les enveloppes réellement produites par les hôtes, pas une instance simplifiée inventée dans le test. Le chat [Conversations](../../../extensions/native/conversations/ui/widget-message.tsx) fournit `host: 'creezio'`, la même instance au résultat initial et au bridge, ainsi que les identifiants de conversation/message ; son `toolInput` permet de corréler instance et audience. Il ne fournit pas d'URI ni de digest de ressource dans cette instance. Ses actions directes renvoient `creezio.widget.action.v1` avec état et résultat, sans nouvelle instance : les rattacher à l'instance initiale et à la requête encore courante dans le pont. Le [transport MCP externe](../../../core/mcp/http.ts) fournit `host: 'external-mcp'`, `invocationRequestId`, URI et digest de ressource. Un appel direct à un outil lui-même lié à un widget peut renvoyer une nouvelle enveloppe de rendu et un nouvel `instanceId` : valider son identité, sa ressource et l'objet demandé avant d'en extraire les données, sans exiger l'ancien identifiant d'instance. Couvrir rendu initial, lecture directe, mauvaise audience/ressource/objet et résultat périmé dans les suites du module. Le test doit exécuter son décodeur et ses actions ; une recherche de chaîne dans le fichier ne prouve pas ces parcours.

Après P0 et le GO applicable, exécuter composants, parcours navigateur et intégration hôte selon l'impact. Vérifier plusieurs widgets d'un même module, leurs trois modes dans Creezio/GPT, contexte remplacé/retiré, hôte sans capacité et timeout sans doublon. Vérifier aussi deux fiches distinctes, navigation rapide, brouillon, portail, refus au clic et historique du widget. Conserver versions, révision et limites dans les preuves ; aucun résultat mocké ne qualifie l'hébergement ou ChatGPT.

## Session navigateur commune

Réutiliser le [SDK access](../../../sdk/access/README.md) pour une entrée native, y compris dans un front personnalisé. L'hôte impose l'audience depuis la composition ; une session admin ne donne pas un rôle. Seul un GET frais établit l'identité affichée. Une panne réseau ne vaut pas anonymat confirmé ; une erreur de mutation reste visible. Purger les secrets saisis, invalider les réponses anciennes et ne pas rétablir un état privé périmé. Un abort ou un démontage ne neutralise pas Set-Cookie : conserver la coordination d'un POST émis et de sa relecture jusqu'à leur règlement, sans retry automatique. Les invalidations entre onglets ne transportent aucune identité à adopter. Documenter les limites du repli sans Web Locks et du déchargement complet. Tester rendu, courses contrôlées et navigateur séparément ; des événements synthétiques ne prouvent pas un changement réel de focus de l'hôte.

## Dépendances entre modules

Appliquer le [contrat commun](../../../docs/DEPENDANCES-MODULES.md). Déclarer les contributions conditionnelles liées aux intégrations facultatives. L’absence du fournisseur retire les opérations, outils, vues ou actions concernés sans casser les autres widgets du module. Un widget historique et une URL directe restent contrôlés au serveur ; ne pas se contenter de masquer un bouton. Le front ne résout pas ses propres versions de modules.
