# T21 — Pages et navigation

`creezio.pages-navigation` reprend les éditeurs, composants de landing et cinq familles de sections du Creezio original. Les six modèles D1 décrivent les pages, la navigation, les métadonnées de fichiers, les liens du brouillon, le marqueur de publication et ses références médias. Les opérations déclarées partagent validation, permissions, révisions et idempotence entre workspace, API et MCP ; le front thémé compose automatiquement sa contribution.

Publier produit un snapshot distinct du brouillon. Modifier le brouillon ne change pas silencieusement la version publiée. Les médias restent des objets privés R2 référencés par leur preuve native. Les liens et le contenu des sections sont validés et bornés ; les conflits de révision empêchent d'écraser une modification concurrente. Le journal SDK et les états de panneau conservent les commandes incertaines et les saisies entre onglets, y compris un JSON temporairement invalide pendant son édition.

Les suites du module passent 22 contrôles ; les widgets sont explicitement non applicables. L'intégration D1 réelle vérifie brouillons, snapshots et frontières d'accès. Sur le profil Linux à 13 modules du candidat `589a827`, le navigateur a enregistré deux révisions de brouillon, publié la révision 1, puis repris un brouillon en révision 4. Il a sauvegardé et publié la navigation éditoriale ; le front authentifié `/pages` a affiché la section hero et le lien. Cette preuve concerne le code UI `589a827`, pas une publication hébergée.

La tranche suivante compose la navigation éditoriale dans `front.header` via les slots déjà acceptés par les deux thèmes, sans branche dédiée dans un thème. Une lecture `page.published.resolve` utilise l'égalité sur le slug publié dans le contexte courant ; le port D1 interdit de trier par ce champ nullable, donc la lecture ne fournit aucun `order.indexId`. Un lien portant `pageSlug` est vérifié lors de la publication de la navigation et rendu avec l'ancre canonique `/pages?slug=...` dès l'affichage. Les anciens liens `href:'/slug'` ne peuvent être automatiquement distingués des routes d'un autre module : leur clic simple conserve la résolution dynamique, tandis que copie et nouvel onglet gardent `/slug` jusqu'à une édition explicite et une nouvelle publication. La route canonique garde la sélection après rechargement, même hors des 50 premiers résultats. La vue active pose temporairement title, description et canonical à partir du snapshot publié puis restaure les valeurs précédentes lorsqu'elle se désactive. Ces changements sont validés par les suites du module et une intégration D1 ciblée ; aucune nouvelle recette navigateur ou Site n'est revendiquée à ce stade.

La lecture du front requiert toujours une identité native. Publication anonyme, distribution publique des médias et SEO serveur indexable restent à réaliser via des ports hôte explicites. Aucun média n'avait été téléversé dans la recette Linux historique ci-dessus. Les outils MCP existent sans renderer de widget propre ; cette absence est déclarée et testée, sans prétendre avoir qualifié une UI ChatGPT. La frontière hôte encore requise est détaillée dans `outputs/CREEZIO-T21-PUBLIC-LANDING-GAP-2026-09-28.md`.

## Images privées du snapshot publié — candidat du 30 septembre

Les mêmes préfabriqués affichent les images privées du hero, son logo et les éléments de fonctionnalités. L'administrateur sélectionne les médias joints ; l'aperçu du brouillon utilise son accès fichier existant. Le front authentifié et l'aperçu publié utilisent le port commun `downloadLinked` du SDK. Les URL externes continuent de fonctionner ; un échec de lecture privée ne provoque aucun repli vers une URL publique.

`page.publish` conserve uniquement les références exactes citées dans les sections actives, dans la limite de cinq images différentes. Deux nouveaux modèles, `page_publication` et `published_page_media`, et un index sont générés centralement ; les définitions SQL des tables existantes restent identiques. Le changement de page, le marqueur et les liens publiés sont validés dans le même lot D1 avec garde de révision. Modifier ou détacher un média du brouillon ne change pas les liens publiés ; `page.reset` restaure les liens nécessaires sans copier les objets R2.

Le candidat passe les six suites : backend 10, UI 12, API/MCP 2, contrat widgets non applicable 1, package 1 et documentation 1. L'intégration D1/R2 réelle vérifie les lectures d'un autre utilisateur autorisé, les refus hors contexte ou référence, les médias du brouillon non exposés, la conservation après détachement, le reset, le remplacement et la concurrence de publication. Le test du remplacement de cinq images vérifie les 12 plans et le budget de 25 unités ; l'aperçu couvre aussi six médias joints pour une seule image sélectionnée. Typage et génération SQL sont vérifiés.

Les lectures refusées n'ont produit aucune mutation de page, et leurs sessions sont déconnectées.
