# Réalisation T16 — widgets des modules

T-16 / US-16, REQ-1601 à REQ-1607. Branche `core/t16-widgets` depuis main `42efa820`. Développement parallèle du catalogue/MCP, du moteur/D1 et du SDK/UI ; intégration, publication et recettes par l'orchestrateur. Cette fiche décrit le raccord en construction, sans annoncer une qualification acquise.

Le module conserve ses opérations, modèles, écrans, dépendances et droits. Sa partie plugin expose ses outils et plusieurs widgets MCP Apps. Le chat Creezio reprend le panneau original ; il héberge les mêmes ressources HTML compilées que les clients MCP. Le workspace et le front montent le même provider public du SDK. Aucun catalogue HTML complet n'est embarqué dans le JavaScript public du front : une projection native filtre audience, contexte et permissions ; chaque ressource est relue sous les droits courants.

Le tour peut enchaîner jusqu'à quatre lectures d'outils puis une réponse finale, par étapes explicites demandées par le client. La chaîne des appels et résultats est conservée dans l'outbox, bornée à 24 Kio ; une reprise connue ne répète pas un effet. Cette borne étend le témoin à un seul outil de T15. L'actualisation terminale et l'ouverture de l'historique chargent les pages récentes jusqu'au dernier message utilisateur, avec au plus 32 pages, pour inclure les widgets intermédiaires et conserver la pagination antérieure.

Chaque action choisit son comportement déclaré : message proposé puis envoyé volontairement, contexte remplaçable/supprimable pour le prochain tour, ou action directe. Une action directe utilise les opérations communes ; un changement purement visuel peut rester dans le widget. La confirmation de transport ne vaut pas succès métier. Une réponse incertaine se réconcilie par sa clé d'exécution ; aucun deuxième envoi implicite ni changement d'adaptateur après émission.

Le helper public `widgetModelContextPayload` adapte uniquement le transport du contexte : l'hôte Creezio reçoit la référence d'action déclarée, tandis qu'un hôte MCP Apps externe reçoit le contenu standard. Un retrait externe transmet un objet vide, sans conserver les données à retirer dans un marqueur de commande. Les mêmes renderers et opérations métier sont utilisés dans les deux hôtes.

Un message conserve un snapshot JSON borné à 4 Kio, une à quatre instances et les identités/digests exacts. Le pointeur `renderExecution` associe module, opération, digest du contrat et identifiant de l'exécution réussie ; il est créé par le cœur. L'hôte relit le résultat durable autorisé pour le premier affichage comme après rechargement. Aucune colonne supplémentaire ne copie le résultat métier. Une exécution expirée ou révoquée, ou une ressource historique absente, reste indisponible sans rejouer l'opération ni substituer une autre version. Les identités de conversation et les droits viennent du serveur, jamais d'un identifiant fourni par le modèle.

Les widgets internes utilisent le pont officiel MCP Apps et une origine d'affichage distincte. Le même relais statique fonctionne en local et sur Cloudflare ; il ne possède ni base, ni clé, ni session applicative. Ses profils CSP et ses origines parentes sont compilés. Le profil de sécurité est indépendant de l'empreinte HTML : ajouter une ressource avec le même profil ne crée pas un nouveau déploiement du relais. L'application reçoit son origine par `CREEZIO_WIDGET_SANDBOX_ORIGIN`. Les données sont transmises en mémoire au widget autorisé et ne sont pas enregistrées par le relais. Ce composant d'affichage n'est pas une deuxième application métier.

Une approbation humaine n'est demandée que si l'opération la déclare. Elle s'affiche dans l'interface native, sous la session de l'utilisateur, avec les valeurs liées à l'opération et un nonce de décision. Le pointeur `approvalId` reste hors de l'entrée métier (`x-creezio-approval-id` en HTTP, métadonnée `creezio/approvalId` en MCP). Le moteur vérifie le grant et le consomme dans le même batch que la mutation. Un widget, un modèle ou un jeton délégué ne peut pas prendre la décision humaine.

Lorsqu'un outil MCP OAuth reçoit `approval_required`, le transport prépare le grant lié à sa requête exacte et renvoie le lien natif dans le texte ainsi que la métadonnée `creezio/approval`. Ce lien n'autorise rien : la page demande la session Creezio du bon compte et relit l'aperçu serveur. Après décision, le client conserve l'entrée et la clé originales pour reprendre ; le LLM ne reconstitue pas la requête. Le pointeur explicite reste utilisable, mais le serveur peut retrouver le grant approuvé par ses liaisons exactes pour un client qui ne relaie pas de métadonnée applicative. Cette recherche ne s'applique qu'au refus avant exécution, jamais à une mutation dont le résultat serait incertain. La décision n'exécute pas elle-même l'opération. Une machine ne devient pas un humain par cette route.

Le tour du chat reçoit le même moteur d'opérations complet que les API, avec inventaire des modules, fichiers, fournisseur et approbations. Il ne reconstruit pas un moteur partiel : le widget du catalogue utilise ainsi le service natif existant.

La recette locale du 27 septembre a affiché les trois widgets de deux modules avec de vrais appels OpenAI. Lecture et modification directes, proposition de message dans le brouillon puis envoi volontaire, remplacement et retrait du contexte ont été exercés. Une réponse PATCH réussie a été coupée : après rechargement et réouverture de l'historique, une lecture du statut retrouve la révision 2 sans seconde mutation. Les essais initiaux rejetés et les artefacts distincts sont conservés dans les preuves externes T16 ; ils ne sont pas remplacés par la dernière réussite.

Le compilateur intègre le JavaScript des ressources sans interpréter ses marqueurs de remplacement et partage les mêmes octets HTML entre catalogues widget et MCP. La déclaration TypeScript des validateurs générés évite de faire analyser leur immense graphe de contrôle JavaScript par TypeScript, sans retirer la validation à l'exécution. Les plafonds locaux de taille sont réévalués sur les trois renderers réellement compilés ; ils ne représentent pas un quota d'hébergeur.

L'évolution du schéma Sites reste centrale : ajout de tables/index et de colonnes explicitement nullables, préservation des fichiers SQL déjà appliqués, refus des transformations incompatibles. Le texte exact produit par SQLite après ALTER est conservé pour l'inspection opérateur, séparément du modèle canonique. Aucun script de migration n'est ajouté aux modules.

La qualification complète doit également couvrir les droits et leur révocation, les deux interfaces Creezio et la connexion ChatGPT réelle. Les tests locaux, les observations navigateur, les preuves Sites et la recette ChatGPT restent distincts. La décision d'approbation native est contrôlée séparément des actions sans approbation du témoin. Le module de recette optionnel ne devient pas un module natif imposé au démarrage du kit.
