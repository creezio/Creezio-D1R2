# Installation et publication sur Sites

Le propriétaire s'inscrit au registre, télécharge le jeton d'une installation de cible `sites`, puis l'importe avec `npm run registry:connect -- --file /chemin/prive/jeton.json --origin https://registre.example.com --target sites`. Le fichier privé `.creezio/registry/installation.json` est lu par `createSitesRegistryContext({root})` de `scripts/sites/registry.mjs` (racine absolue du checkout). Ce helper retourne `registryIdentity`, `registryClient`, `publicationJournal` et `publicationGate`. Le publisher GPT utilise cette gate avec `target: 'sites'` avant sa publication native puis lui transmet le reçu réel ; une déclaration perdue se reprend sans republier. Ce raccord ne crée pas de mécanisme de publication depuis le back-office. Voir le [guide du registre](../services/registry/README.md).

Le profil Sites utilise le même Worker, les mêmes modules et les mêmes comptes que les autres hébergements. Seuls les bindings logiques DB/BUCKET, le profil de compilation et le parcours opérateur changent. `configuration/composition.sites.json` sélectionne le socle natif et le thème ChatGPT-like ; les vues métier synthétiques des tests n'y figurent pas. La composition `configuration/composition.sites-qualification.json` ajoute uniquement Catalogue, Stripe et Meili pour une qualification distincte après la première publication native. Le profil natif reste la valeur par défaut. L'origine et les secrets sont des variables du déploiement, sans valeur propre à un compte dans le dépôt générique.

La cible se lit depuis le manifeste `.openai/hosting.json` du Site sélectionné. Un changement de compte GPT qui rend une ancienne cible inaccessible autorise une nouvelle cible publique, avec conservation de sa provenance ; les publications suivantes réutilisent cette cible. Les sources et données de l'ancien Site sont préservées.

Dans un checkout neuf sous Node 24, exécuter `npm ci --ignore-scripts` puis `npm run sdk:build` avant `npm run build:sites`. Le build Sites prépare le schéma central et compile le Worker commun avec la composition Sites. Par défaut, le manifeste est celui du checkout courant ; `CREEZIO_SITES_MANIFEST` peut indiquer le chemin absolu du manifeste du Site sélectionné. Cela permet de réutiliser les dépendances du checkout de développement. Le résultat reste dans son unique `dist/`. Si la source Git publiée est ce checkout, son commit inclut les fichiers applicatifs et le journal DDL de la cible. Pour un staging Git distinct, utiliser le préparateur de source ci-dessous après le build Sites, puis figer le commit propre du staging avant publication. Ne copier ni dépendances, ni données locales, ni secrets.

### Source d'un staging Git distinct

`scripts/sites/source.mjs` relie le commit du constructeur Core et son reçu `.quality/sites-build.json` au commit de source du Site. Il exige trois répertoires absolus distincts et non imbriqués : checkout Core propre, descripteur de cible dont le schéma Sites a été préparé, et staging Git propre du **même** `project_id`. Le `dist` courant doit être celui du build Sites pour cette cible ; un build local ou Docker ne le remplace pas. Les plans et reçus sont de nouveaux fichiers hors de ces trois répertoires.

```text
node scripts/sites/source.mjs plan --site <descripteur-absolu> --stage <staging-absolu> --plan <plan-nouveau-absolu>
node scripts/sites/source.mjs prepare --plan <plan-absolu> --receipt <reçu-préparation-nouveau-absolu>
# Examiner le diff, puis committer manuellement le staging dans son dépôt.
node scripts/sites/source.mjs verify --plan <plan-absolu> --receipt <reçu-préparation-absolu> --verification <reçu-vérification-nouveau-absolu>
```

Le plan enregistre avant copie les identités Git Core/staging, les empreintes des fichiers et les suppressions autorisées. `prepare` revérifie ce plan, copie uniquement les sources Git approuvées et les métadonnées/DDL générés validés, puis adapte de façon déterministe le script `build` du `package.json` au profil sélectionné et à son verrou. Sans option, il conserve `configuration/composition.sites.json`. Pour le profil facultatif, construire avec `CREEZIO_COMPOSITION=configuration/composition.sites-qualification.json` et `CREEZIO_COMPOSITION_LOCK=configuration/composition.sites-qualification.lock.json`, puis ajouter `--composition configuration/composition.sites-qualification.json` à la commande `source.mjs plan`. Le plan refuse une composition dont l'empreinte diffère du build ; `prepare` et `verify` conservent cette sélection. Un fichier présent mais non suivi, même ignoré, n'est jamais écrasé. Un ancien fichier suivi n'est retiré que si une provenance de source du même projet en atteste déjà le chemin et les octets. Une interruption laisse le staging Git modifié ; vérifier son état et revenir explicitement à une base propre avant tout nouveau plan. `verify` exige le staging committé, propre, descendant de sa base Git et contenant exactement les octets prévus ; son reçu lie `CoreSHA` à `SiteSHA` et aux digests du build/DDL. Le préparateur ne crée ni commit, ni Site, ni archive de publication et ne pousse rien.

Le build applicatif vérifie désormais chaque migration et instantané du journal central `db/creezio-schema-history.json`, puis place le manifeste d'hébergement et ces fichiers sous `dist/.openai`. Le build autonome de l'opérateur, généré par `scripts/sites/prepare-operator.mjs`, fait le même contrôle. Il refuse un `dist` opérateur avec des fichiers supplémentaires. Le nombre de migrations suit l'historique réel du Site : il n'est pas figé au premier déploiement. La mesure Worker/assets de `measureRuntimeArtifacts` reste séparée de l'empreinte des métadonnées Sites, enregistrée dans `.quality/sites-build.json`.

Après avoir figé et validé les sources du Site, `node scripts/sites/export.mjs --kind operator --site <répertoire-absolu-du-Site> --archive <archive-absolue> --receipt <reçu-absolu>` produit l'archive des seuls artefacts construits de l'opérateur. Après `npm run build:sites`, employer la même commande avec `--kind app` pour l'application. Les deux chemins de sortie doivent être nouveaux et hors des sources. L'exporteur vérifie le reçu du build, les fichiers `dist/server` et `dist/client`, les métadonnées `dist/.openai` et le journal DDL, puis archive uniquement `dist/` ; le reçu applicatif conserve l'identité Git du checkout qui a construit l'application et les empreintes de chaque fichier. Il refuse une source applicative non figée ou un fichier manquant, altéré ou supplémentaire. Si le Site est poussé depuis un staging distinct, rapprocher le reçu `source.mjs verify` (commit Site) et le reçu `export.mjs` (commit constructeur, build et métadonnées) avant publication. L'exporteur ne copie pas le projet, ne pousse pas cette source Git et ne publie rien par lui-même.

## Schéma central

`scripts/sites/schema.mjs` reçoit le plan de composition approuvé. Il génère les déclarations actuelles dans `db/schema.ts`, et emploie le journal DDL personnalisé de Drizzle pour conserver exactement les contraintes et les tables WITHOUT ROWID produites par le compilateur commun. Ce n'est pas un deuxième modèle de données à maintenir. Les auteurs de modules ne fournissent aucun script de transformation.

Les fichiers générés SQL, instantanés et journal sont versionnés avec la source du Site. La génération initiale crée les objets ; les suivantes ajoutent les nouveaux objets ou des colonnes explicitement nullables sans défaut, et conservent les objets retirés de la composition. L'historique garde la déclaration canonique et le texte exact attendu dans `sqlite_schema` après un `ALTER TABLE`, pour que l'inspection de l'opérateur reste stricte. Les contraintes et définitions existantes doivent rester identiques ; suppression, renommage, changement de type ou ajout obligatoire sont refusés. Aucun jeu de données, compte ou clé n'est inséré dans le DDL. Les fichiers déjà appliqués sont immuables ; le fournisseur peut avoir appliqué du SQL avant une publication Worker échouée.

## Premier compte

L'outil `scripts/sites/prepare-operator.mjs` produit un artefact opérateur distinct pour la cible neuve. Il réutilise les services natifs de première installation. Son unique commande exige un jeton secret, une origine HTTPS exacte, une échéance maximale d'une heure et le plan attendu. Il compare les définitions réelles de la base, y compris les objets propres à l'hébergeur préalablement inspectés, avant toute écriture ; le contrôle accompagne les batchs.

Une installation consommée renvoie son compte existant. Une réponse perdue se réconcilie par inspection et ne remplace pas le compte. Si l'interruption précède la consommation de la capacité native, l'état `capability_pending` est conservé jusqu'à expiration de cette capacité ; l'opérateur ne réarme pas une capacité encore vivante. Cette limite de disponibilité ne permet ni reset ni création d'un deuxième propriétaire.

Après création du compte, publier le Worker applicatif ordinaire sur le même Site, puis retirer les secrets de l'opérateur. `worker.ts` n'importe jamais l'installateur et ne contient aucune route bootstrap permanente. La recette doit confirmer la connexion au compte conservé après remplacement de l'artefact et la disparition de la route opérateur.

## Publication et preuve

Avant chaque publication, contrôler les variables et secrets du Site cible : `CREEZIO_APP_ORIGIN` doit être l'origine HTTPS canonique actuelle, `CREEZIO_RUNTIME_PROFILE` doit valoir `sites`, et le coffre requis par les modules sélectionnés doit conserver sa clé serveur (`CREEZIO_VAULT_KEYRING` pour OpenAI). Si la composition sélectionne des widgets, définir `CREEZIO_WIDGET_SANDBOX_ORIGIN` vers l'origine HTTPS distincte de leur relais et vérifier que ce relais autorise l'origine actuelle de l'application. Une configuration absente peut laisser le déploiement réussir tout en faisant échouer les routes applicatives ; qualifier ces routes après publication.

Le contrôle du registre central précède le publisher et journalise sa déclaration. Le parcours avec archive locale publie une version dont la source a été poussée et dont l'archive correspond ; le statut du fournisseur confirme la livraison. Le SHA du commit Site poussé et l'identité Git du checkout constructeur sont deux preuves distinctes lorsqu'un staging est utilisé : leur correspondance de fichiers et de DDL doit être conservée avec le reçu de publication. Une déclaration incertaine se réconcilie sans redéployer. Aucun bouton du CMS ne prétend déclencher une publication Sites.

### Repli officiel : build distant depuis la source

Lorsque le composant officiel de packaging local ne permet pas de produire l'archive, l'API Sites accepte de sauver la version du commit source déjà poussé sans archive. Vérifier avant ce save que le SHA complet correspond au HEAD de la branche source de la cible, que `scripts/sites/source.mjs verify` relie ce commit au constructeur et aux fichiers/DDL, et que le `package.json` et son lock permettent une installation neuve. Conserver l'ID de version renvoyé. La réponse initiale du save sans archive peut laisser `archive_storage` à `null` : elle ne prouve ni build, ni déploiement. Avant l'effet, comparer le journal DDL transporté et l'état du schéma de la cible ; un écart non résolu suspend la publication. Un reçu Docker ou Cloudflare ne vaut pas attestation Sites.

Le mode opératoire `remote-source` du gate existant conserve le contrat du SDK et du service de registre. Son `artifactDigest` est l'empreinte SHA-256 de l'inventaire exact des fichiers source transportés, validé par `verifySitesSource` ; ce n'est **pas** l'empreinte du Worker binaire distant. `sourceSha` désigne le commit Site poussé. Le gate lie ce digest, le commit constructeur, la composition et la cible à une même clé de publication. Il obtient le préflight du registre **avant le déploiement** de la version sauvée. Après l'effet, l'opérateur lit le reçu du fournisseur avec les outils officiels et le remet au gate ; celui-ci vérifie même projet, même ID de version et commit source, statut `succeeded` et URL canonique attendue, puis déclare au registre sous la même clé. Une réponse perdue ou incertaine se réconcilie à partir des identifiants déjà reçus, sans nouveau save ou déploiement aveugle. Les exigences [REQ-0801 à REQ-0803](EXIGENCES.md#REQ-0801) restent applicables.

Après le build distant, Sites peut renseigner `archive_storage.content_hash` pour l'archive qu'il a produite. Cette empreinte fournisseur reste distincte de l'`artifactDigest` de la source transportée et ne constitue pas une mesure locale des octets du Worker. Ces preuves établissent l'identité de la source envoyée et le résultat déclaré par le fournisseur, sans attester directement le binaire Worker. Garder séparés version sauvée, déploiement `succeeded`, registre synchronisé et recette fonctionnelle. Qualifier le runtime réellement actif et la conservation des comptes/données avant d'annoncer la livraison de cette nouvelle version.

Le parcours a été exécuté sur une cible neuve : l'application a remplacé l'opérateur, le même compte natif se connecte et l'ancienne route opérateur renvoie 404. Les réponses OpenAI du workspace et du front, la persistance du brouillon et la relecture R2 ont leurs preuves hébergées propres. La recette finale du candidat reste distincte de ces étapes intermédiaires ; voir [la qualification Sites](QUALIFICATION-SITES.md).
