# T28 — Connexion et diagnostic d'une instance Meili externe

Le module optionnel fournit une **connexion** puis un diagnostic de liste d'index, pas un moteur de recherche. Creezio ne fournit, n'installe et ne maintient aucun service Meili. L'application reste utilisable sans lui ; la recherche déjà livrée par le Catalogue continue d'utiliser ses propres opérations. La recherche globale native T05 est reportée et demande une explication puis un accord distinct avant son raccord.

Le module `creezio.meili` reprend la carte de réglages de recherche de l'interface originale. Un administrateur autorisé configure une origine HTTPS et une clé API dans le contexte courant. La configuration D1 est versionnée ; la clé est scellée dans le coffre natif et n'est ni renvoyée par les opérations ni conservée dans le panneau. Les commandes de réglage ont une clé de demande et une révision attendue. Changer l'origine exige d'abord la révocation de la clé existante, même si la connexion est désactivée ; l'administrateur fournit ensuite une nouvelle clé pour la nouvelle origine. Révocation, changement de session, d'audience ou de contexte empêchent de réutiliser un ancien état de vue.

La première lecture distante `connection.check` déclare `GET /indexes?limit=1` avec authentification Bearer et borne la réponse JSON. Elle retourne seulement la confirmation d'accès, sans nom d'index, document, total ou corps fournisseur. Elle ne prouve aucune indexation métier. La tranche 0.2.0 ajoute `index.list` : une page GET `/indexes` de 20 entrées au maximum, avec offset et limite bornés, ne projetant que UID, clé primaire, dates, total fournisseur et curseur. Elle exige `creezio.meili:manage` en audience admin ; `meili.read` seul est refusé. Le module relit la configuration après le GET pour refuser une réponse obtenue pendant une rotation ou une révocation. La carte de réglages d'origine affiche ce diagnostic sur demande, sans recherche de documents, widget ni nouveau raccourci. Aucune URL, méthode ou requête arbitraire n'est fournie au handler.

Un GET direct unique vers une instance Meili autorisée a répondu HTTP 200 avec une enveloppe conforme ; le reçu expurgé `CREEZIO-T28-MEILI-EXTERNAL-READONLY-2026-09-29.json` ne contient aucun identifiant d'index ni secret. La PR #53 a passé 1 247/1 247 contrôles. Sur Linux, la recette du code `3b2131c` a adopté les deux seules tables Meili, confirmé quatre intentions de configuration et affiché « Connexion Meilisearch vérifiée » dans l'interface après un contrôle réel. Le premier résumé du helper PowerShell était ambigu malgré une exécution HTTP réussie ; la confirmation UI et le reçu expurgé `CREEZIO-T28-LINUX-RECIPE-3B2131C-2026-09-29.json` bornent cette preuve. Aucun index, tâche distante, document ou service Meili n'a été créé par cette recette. La nouvelle lecture paginée 0.2.0 passe ses six suites locales et une intégration D1/coffre/API/MCP simulée ; elle n'a pas encore été exercée contre le fournisseur ni livrée sur Linux/Cloudflare/Sites.

REQ-2801 reste ouverte. L'indexation incrémentale, les suppressions, une reconstruction reprenable par génération et les tâches asynchrones Meili requièrent une tranche d'écriture durable ; un HTTP 202 ne suffit pas à confirmer leur effet. Recherche de documents, facettes et compteurs demanderont des filtres de contexte appliqués avant agrégation et une réautorisation des résultats. Les déclarations de recherche présentes dans les contrats n'ont pas encore ce consommateur runtime ; ce module ne les active pas fictivement. Le bouton « Réindexer » reste indisponible avec une explication dans l'interface. La recette de recherche/indexation native et les profils hébergés restent à réaliser avant de clore T28.
