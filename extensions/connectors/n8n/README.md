# Connecteur n8n externe

Ce module relie Creezio à une instance n8n déjà exploitée par l’administrateur. Il ne lance, n’installe et ne maintient pas n8n. Dans l’espace de travail, l’administrateur enregistre l’URL HTTPS de l’instance et sa clé API n8n ; le coffre natif chiffre la clé, et seul l’hôte l’ajoute aux requêtes autorisées. La clé n8n ne sert jamais à appeler l’API Creezio.

Une origine ne peut pas changer tant qu’une clé reste scellée, même si la connexion est désactivée. Pour changer d’instance, révoquer la clé dans Creezio, enregistrer la nouvelle origine, puis fournir une clé pour cette instance. Chaque étape conserve sa révision attendue et sa clé de demande ; la révocation locale n’efface pas la clé distante.

Selon la [documentation n8n sur les clés API](https://docs.n8n.io/connect/n8n-api/authentication/), l’API n’est pas disponible pendant l’essai gratuit ; les clés non Enterprise peuvent avoir accès à toutes les ressources du compte. Choisir une clé et un compte adaptés aux droits consentis, puis révoquer la clé dans n8n si elle ne doit plus servir. La révocation dans Creezio désactive sa référence dans le coffre et bloque les appels du connecteur ; elle ne supprime pas la clé à distance.

La première surface expose `config.read/set`, `config.key.set/revoke`, `connection.check`, `workflow.list/read` et `execution.list/read` en UI, API et MCP selon les droits. Les lectures distantes utilisent l’[API publique n8n](https://docs.n8n.io/connect/n8n-api/) version `/api/v1` et projettent uniquement les métadonnées : aucun nœud, credential, donnée d’exécution ou contenu épinglé n’est renvoyé. La pagination n8n utilise un curseur opaque. Une réponse distante trop grande ou mal formée échoue clairement, sans troncature silencieuse.

Un administrateur peut autoriser une origine HTTPS par contexte et attribuer séparément `n8n.manage` (admin) et `n8n.read` (admin/app). Les appels machine via token API ou MCP restent soumis aux mêmes permissions. Une instance désactivée, une clé absente/révoquée ou un coffre indisponible refuse l’accès distant. Les accès sortants passent par le port connecteur de l’hôte : chemins/méthodes/en-têtes fixés au build, une requête distante au plus par opération, refus des redirections, origines locales et adresses IP littérales, bornes de temps et d’octets. Il n’y a pas de garantie DNS fondée sur une simple vérification préalable.

Le déclenchement utilise un second descripteur `n8n.webhook.v1` et un coffre dédié. L’administrateur configure l’origine HTTPS, l’ID du workflow et un **seul segment** de chemin de production `/webhook/{id}`. Il configure dans n8n un Webhook node publié avec authentification Header `X-Creezio-Webhook-Key`, puis un `Respond to Webhook` renvoyant `{intentId,executionId}`. L’[URL de test n8n](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/) n’est pas utilisée. La clé API n8n ne part jamais dans ce POST. Aucun callback n8n n’est supposé signé nativement.

Un utilisateur admin ou app doté de `n8n.trigger` prépare une intention locale, puis confirme son unique émission. La connexion API de suivi doit être active à la même origine que le webhook. Le corps JSON est figé dans D1 (8 Kio maximum), la fenêtre d’émission est de 15 minutes et la révision/clé/activation du webhook sont revérifiées. La connexion API est relue avant le POST ; sa désactivation ou la révocation de sa clé désarme atomiquement le webhook et invalide les intentions préparées. Le lot de confirmation contient aussi une garde atomique de la configuration API réellement relue : si elle change après le POST, l’issue est inconnue, jamais faussement acceptée. Un 2xx avec l’ID d’intention exact et un ID d’exécution valide signifie uniquement **accepté** ; il ne prouve pas la fin du workflow. Une lecture distincte de `/api/v1/executions/{id}` projette le statut après vérification du propriétaire, du contexte, de l’origine et du workflow. Après timeout ou réponse non corrélée, le journal conserve l’issue inconnue et le même déclenchement n’est pas rejoué. L’écran de suivi et les deux widgets (workflows, intention) ne divulguent ni corps d’exécution ni secrets ; les widgets n’émettent aucune commande. Le rendu du chat interne est lié à son instance et à son audience ; la relecture directe y retourne une action sans instance. Le rendu MCP externe reste lié à son URI et à son empreinte de ressource.

La publication/dépublication des workflows, les callbacks dédiés, stop/retry/delete et les règles T24 restent à qualifier. L’API REST publique ne propose pas d’exécution générique de workflow. Un appel n8n vers Creezio peut employer un token machine/API/MCP Creezio autonome, sans utiliser ces clés fournisseur. Le paquet et les tests simulés ne prouvent pas une recette avec instance n8n réelle ; cette recette est reportée à la demande de l’utilisateur.
