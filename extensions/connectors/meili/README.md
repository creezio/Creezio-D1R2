# Meili — projection Catalogue externe

Le module utilise une instance Meilisearch HTTPS existante. L’administrateur configure son URL et une clé API scellée dans le coffre natif. Aucun service Meili n’est installé. La connexion et le diagnostic d’index restent limités aux droits administratifs.

La projection `catalog-products` lit les produits du Catalogue dans leur contexte et sous le droit `catalog.view`. Le contrat de recherche du Catalogue déclare les champs, la facette catégorie, la version de projection et sa dépendance facultative `creezio.meili`. Sans intégration sélectionnée, le Catalogue conserve sa recherche D1 `product.search`.

Une nouvelle génération obtient un UID dérivé du contexte et de l’exécution. `index.prepare` parcourt une page de 50 produits, conserve les brouillons et archives comme suppressions, compare les révisions déjà confirmées et fige au plus 13 documents dans `index_job` avant tout appel externe. `index.emit` envoie le lot une seule fois avec la clé figée ; Meilisearch répond par une tâche 202. `index.reconcile` vérifie l’UID, le type, l’index et le succès de cette tâche avant d’avancer le curseur et les révisions locales. Les écritures distantes sont exclusivement les routes déclarées `POST /indexes/{id}/documents?primaryKey=id` et `POST /indexes/{id}/documents/delete-batch`. La clé primaire est fixée dans la requête par le descripteur du port hôte, même si les documents contiennent d’autres champs finissant par `id`. [Meilisearch applique ce paramètre au premier ajout](https://www.meilisearch.com/docs/reference/api/documents/add-or-replace-documents#query-parameters) ; une clé primaire déjà établie sur l’index doit donc être vérifiée séparément. Aucun index distant n’est effacé par l’abandon.

Si l’émission a une issue inconnue, la clé ne peut pas être remplacée pour rejouer le même lot. L’administrateur inspecte le statut de la commande ; il peut ensuite abandonner explicitement la génération, qui reste en quarantaine, en conservant l’ancienne génération active. Une synchronisation incrémentale repart de l’index actif et n’émet que les révisions modifiées. L’interface administrative montre les étapes et exige une action pour chacune.

`index.search` lit uniquement l’index actif du contexte et de la source déclarée. Les ID de hits sont relus sur le modèle propriétaire avec une nouvelle vérification de permission avant de renvoyer les champs. Les totaux et facettes bruts de Meilisearch sont écartés : `pageCount` et `facets` ne décrivent que les hits autorisés de cette page ; ils ne sont pas des totaux globaux. La recherche globale native T05 reste un projet distinct, reporté par l’utilisateur.

Le widget MCP Apps `search-results` montre uniquement ces hits relus et propose une recherche directe sur la même source. Les champs sont insérés comme texte ; il n’y a ni HTML fournisseur, ni image, ni total global. La même opération `index.search` sert l’API, le MCP et le widget.

Le [GET de liste d’index Meilisearch](https://www.meilisearch.com/docs/reference/api/indexes/list-all-indexes) a été vérifié sur une instance externe (HTTP 200 ; reçu expurgé `CREEZIO-T28-MEILI-EXTERNAL-READONLY-2026-09-29.json`). La première émission réelle, tâche 165, a échoué avec `index_primary_key_multiple_candidates_found`. Après correction de `primaryKey=id`, la recette réelle `CREEZIO-T28-MEILI-REAL-QUALIFICATION-2026-10-01.json` (hors dépôt) confirme la tâche 166, deux documents, l’état `ready` révision 9 et une recherche API native autorisée. Elle n’exerce pas le widget de recherche.

Dans cette recette, l’interface admin affichait « Aucune source » au premier chargement et après rechargement ; le bouton « Actualiser l’état » révélait bien la source Catalogue et l’état `ready`. Le chargement initial et le rafraîchissement attendent maintenant la configuration avant `index.read`, et une configuration modifiée relit la source courante ou la première source disponible. Cette correction est vérifiée par tests UI locaux ; son comportement dans le navigateur avec le fournisseur réel reste à requalifier.
