- État : construction et qualification autorisées suivant les lots du backlog. Une sonde de qualification n'est pas le produit complet ni la recette finale des deux Sites ; seuls les résultats réellement vérifiés changent l'état d'une tâche.
- Creezio est un produit neuf nativement serverless. Le dépôt contient uniquement sa conception et son code propres. Les modèles décrivent directement les données actuelles ; l'installation initialise une base neuve. Les modules ne contiennent pas de scripts de transformation de bases entre versions.
- Décision acquise : le SQL de création et d'évolution est généré et inspecté dans une chaîne centrale de publication, puis versionné avec la source conformément à l'hébergement. Aucun script SQL de transformation n'est demandé aux auteurs de modules. Préserver les données et bloquer une évolution incompatible ou destructive non résolue.
- Meili, Hermes, n8n, navigateur distant, exécution système et autres services incompatibles avec le runtime serverless sont des extensions optionnelles connectées à des services externes. Aucune dépendance de démarrage du socle à ces services, Docker ou un processus persistant.
- Le back-office/workspace Creezio peut être toute l'interface d'une app personnelle ou collective. Accès au workspace et administration système sont deux droits distincts : les utilisateurs y exercent leurs opérations métier autorisées, sans accès implicite aux comptes globaux/secrets/modules. Le front est facultatif, thémé ou headless ; il utilise les mêmes API. Les thèmes compatibles montent dynamiquement les vues/routes/navigation déclarées par les modules ; aucun ajout de code dans chaque app ou thème pour enregistrer une vue conforme.
- Distinguer MODULE/EXTENSION complet (données propres, logique métier, API, écrans, dépendances et relations intermodules) de sa partie PLUGIN conversationnel (MCP, widgets, skills et manifeste standard GPT). Cette partie utilise les opérations du module ; aucun second backend ni copie des données. Le module reste utilisable sans chat. Le format GPT s'applique à sa partie plugin même sans publication ChatGPT, pas à tout le backend métier.
- Chaque app possède son MCP/plugin d'administration et peut exposer un MCP/plugin distinct pour les utilisateurs métier, dans son workspace ou son front, dans le même déploiement. Catalogues, ressources, skills et droits séparés ; public/front ne signifie pas accès anonyme aux données protégées. Les modules déclarent leurs contributions admin/front, sans exposition administrative automatique. Le chat Creezio héberge plusieurs plugins et route leurs widgets selon la surface et les droits.
- Les Sites Creezio de ce projet et de sa recette sont publics, conformément au choix utilisateur. Le navigateur utilise les comptes/sessions natifs ; les clients externes utilisent un jeton API ou une autorisation MCP, sans cookie ni connexion GPT. Mêmes opérations, droits et contextes serveur ; signatures propres pour les webhooks. Une identité ChatGPT ne crée jamais automatiquement un compte, une session ni des droits applicatifs. Un hébergement public ne rend pas les données ou l'administration publiques.
- Un projet/repo et un déploiement applicatif commun par application ; pas de repo Admin de flotte séparé ni de runtime par client. GPT Sites est la cible principale ; Docker est un adaptateur d'hébergement, pas une dépendance du socle.
- Sur Sites, l'utilisateur ou une tâche GPT explicitement configurée demande la mise à jour dans GPT ; publication puis vérification dans ce parcours. Aucun bouton ou pont de publication Sites depuis l'application. Sur Docker, prévoir le déclenchement depuis le back-office via un module de livraison et un exécuteur limité. Aucune tâche GPT créée implicitement.
- GPT Sites : un couple D1/R2 commun par application, comme un SaaS, avec cloisonnement logique par contexte et droits serveur. Abandonner le provisionnement de plusieurs D1/R2 dans un même Site et sa qualification. Docker : conserver la possibilité de ressources D1/R2 distinctes selon l'application/extensions, sans multiplier les runtimes applicatifs ni imposer un métier au CMS.
- Parcours natifs : GPT Sites avec D1/R2 fournis ; développement/test Docker avec Miniflare et D1/R2 locaux persistants sans compte Cloudflare ; publication COMPLETE sur Cloudflare personnel (Worker backend/API + front/admin/assets + D1/R2), indépendante du local. Miniflare reste un outil dev/test, pas la production. Fournir depuis le back-office local un parcours de publication guidé avec droits Cloudflare adaptés, transfert vérifié des données/fichiers, configuration des bindings/secrets/auth et contrôle final. Les mises à jour suivantes ne réimportent pas le jeu local sur les données de production. Connexion Docker → données Cloudflare également possible, distincte de la publication complète. Lire `docs/STOCKAGE-ET-HEBERGEMENT.md`.
- Extensions : contrat commun couvrant modèles actuels/données, API/MCP, droits, recherche, UI et widgets du chat. Les widgets ne créent pas une seconde logique métier. Une mise à jour ne réinitialise pas les données ; une incompatibilité bloque l'application automatique.
- Widgets : plusieurs types par module et plusieurs instances ; mode par action message/contexte/direct, combinable dans un widget. Lire `docs/INTERACTIONS-WIDGETS.md`. Même contrat dans GPT et chat interne, aucune réponse ou mutation déclenchée par simple contexte, aucun achat validé par un prompt. Contrôle des approbations dans l'opération commune, y compris MCP direct ; timeout != échec certain, pas de repli susceptible de doubler l'effet.
- La compatibilité native ChatGPT est obligatoire dans le contrat des modules : MCP Apps pour l'UI portable, outils exploitables sans UI, skills et paquet de plugin standard. Lire `docs/COMPATIBILITE-CHATGPT.md`. Données et droits restent dans Creezio ; OAuth délégué pour ChatGPT protégé, distinct des tokens d'automatisation et de la clé du module OpenAI. Tester réellement dans ChatGPT avant d'annoncer cette compatibilité. Réutiliser les composants déjà qualifiés avant d'engager une réécriture ; isoler et retester seulement les raccordements dépendant de l'hôte.
- Un module connecteur, notamment n8n ou Stripe, est une intégration prête à configurer : accès fournisseur puis API/MCP, événements, UI et widgets disponibles sans réintégration par l'app cliente.
- Trois familles partagent le même contrat : modules natifs, modules métier communs réutilisables et modules spécifiques. Seuls les modules connecteurs nécessitent un fournisseur ; un module métier autonome n'en dépend pas. Skills de développement et skills conversationnels sont distincts. Les premiers accompagnent des validateurs/contrôles CI et de livraison contraignants pour les parcours officiels ; une instruction à l'IA seule ne garantit pas la conformité.
- Même architecture, modèles et opérations sur Sites, Docker dev/test et Cloudflare direct ; différences encapsulées par capacités/adaptateurs. Sites est limité au D1/R2 commun ; ressources physiques distinctes possibles hors Sites, y compris Cloudflare direct, à qualifier sans runtime par client. Conserver aussi les contraintes de livraison/transport mesurées. Aucun fork de logique métier selon l'hébergeur.
- Le registre central Creezio demandé suit projets/déploiements, propriétaire, URL, dépôt éventuel, origine et versions datées ; il fournit aussi les services de licence/activation. Il ne centralise ni comptes utilisateurs métier, ni données, ni clés fournisseurs, et ne pilote pas une flotte d'apps. Token de déclaration, droits premium signés et autorisation d'assistance sont distincts. Inscription proposée à l'onboarding, obligatoire à la publication officielle, local hors ligne et propriétaire GitHub/email vérifié. Panne de validation avant publication : livraison suspendue, app existante préservée ; déclaration après publication reprenable. Pas de promesse d'inventaire universel de copies modifiées ou non déclarées.
- Création avec GitHub : proposer la connexion si absente et vérifier outil/droits de fork. Sans GitHub : copie d'une release précise et provenance, sans prétendre à un vrai fork ; rattachement ultérieur possible. Réutiliser les sources existantes. Les contributions amont passent par issue/PR autorisée, revue, tests, release et adoption par chaque app ; aucune fusion ou publication client implicite.
- Le chat utilise un module OpenAI activé et configuré avec une clé API conservée côté serveur pour accéder au LLM. Interface, conversations, outils, permissions et widgets restent des capacités Creezio. Sans module actif ou clé valide, aucune réponse IA simulée ; signaler la configuration manquante. La recette du transport du chat et celle du fournisseur OpenAI sont distinctes.
- Creezio ne fournit, n'installe, n'héberge, ne met à jour et ne sauvegarde aucune application tierce n8n/Hermes/Meili. Le module reçoit les accès d'un service déjà disponible auprès du fournisseur ou géré séparément par l'utilisateur. Ni son paquet ni sa démo ne contiennent d'installateur du service.
- Aucun scheduler natif requis, sur Sites comme sur les autres hébergements. n8n ou un service externe planifie et relance les appels API/MCP ; Creezio authentifie, autorise, exécute des opérations bornées et persiste l'état/résultat. Conserver tâches, échéances, approbations, outbox, idempotence et journaux ; ne pas recréer une boucle de traitement autonome. API token et MCP sont natifs, utilisables sans module n8n installé. Le module sert au pilotage et à l'intégration de n8n depuis Creezio. Clé fournisseur et autorisation machine Creezio sont distinctes ; aucune validation humaine contournée par un jeton.
- Préserver les capacités fonctionnelles natives (tâches, messagerie, support, CRM, landing, analytics, navigation, chat et validation humaine) ; externaliser leurs moteurs/transports ne les transforme pas en fonctionnalités optionnelles à réintégrer.
- Écosystème : contrat identique pour extensions officielles/privées/tierces ; version, éditeur et origine explicites ; mise à jour individuelle via build/publication de l'application. Prévoir un starter forkable produisant paquet installable et démo Cloudflare depuis le même code ; pas de Worker imposé par extension. Le SDK headless et les thèmes n'accèdent pas aux composants privés d'administration.

La cible Community/Enterprise est décrite dans LICENCES-ET-OFFRES, avec revue des textes/périmètres avant distribution du code. - Fournir toutes les fonctionnalités et interactions spécifiées du back-office, notamment onglets/workspace et chat. L'admin reste standardisée Creezio ; ne pas y recoder un chat métier propre à chaque app. Personnalisation libre et thèmes (dont ChatGPT-like) uniquement dans le front applicatif, avec backend commun et droits distincts.

Tout pont interne nécessaire reste limité à l'adaptateur et bloque sur version incompatible, sans modification de `node_modules`.
